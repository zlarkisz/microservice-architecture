## Завдання 1 — Sequence діаграма Auth

Діаграма описує три ключові flow системи безпеки:

**Registration** — реєстрація нового користувача з хешуванням пароля та видачею токенів.

**Login** — автентифікація існуючого користувача з перевіркою пароля та генерацією JWT пари (access + refresh токени).

**Authorization** — обробка захищеного запиту через API Gateway з локальною валідацією JWT та автоматичним оновленням токена у разі закінчення терміну дії.

### Учасники діаграми

| Учасник                 | Відповідальність                               |
| ----------------------- | ---------------------------------------------- |
| Client                  | Браузер або мобільний додаток                  |
| API Gateway             | Валідація JWT, маршрутизація запитів           |
| Auth Service            | Видача та оновлення токенів, хешування паролів |
| UserManagement Service  | Зберігання профілів користувачів               |
| OrderManagement Service | Приклад захищеного мікросервісу                |
| Auth DB                 | Зберігання refresh токенів                     |
| User DB                 | Зберігання даних користувачів                  |

### Ключові архітектурні рішення

- **Окремий Auth Service** — відповідальність за токени відділена від управління профілями
- **JWT** — токени містять `userId` та `roles` у payload, сервіси валідують локально без звернення до Auth Service
- **Access Token** — живе 15 хвилин, **Refresh Token** — 30 днів
- **API Gateway** валідує токен один раз для всіх сервісів — мікросервіси не дублюють цю логіку

## Завдання 2 — Ролі користувачів

Система визначає 5 ролей на основі принципу **Least Privilege**:

| Роль                | Опис                                                            |
| ------------------- | --------------------------------------------------------------- |
| **Guest**           | Неавтентифікований відвідувач — лише перегляд публічних даних   |
| **Customer**        | Зареєстрований покупець — повний цикл покупки, лише власні дані |
| **Vendor**          | Постачальник — управління власними товарами та поставками       |
| **Content Manager** | Редактор — управління контентом без доступу до бізнес-логіки    |
| **Admin**           | Адміністратор — повний доступ з обов'язковим audit logging      |

Детальна матриця дозволів → [task2-user-roles/user-roles.md](task2-user-roles/user-roles.md)

## Завдання 3 — Шифрування даних

Дані розділені на три категорії залежно від рівня чутливості:

**Критичний рівень** — обов'язкове шифрування/хешування:

- Паролі → хешування bcrypt
- Номери банківських карток → AES-256
- CVV коди → не зберігаються взагалі (вимога PCI DSS)
- Refresh токени → хешування SHA-256

**Середній рівень** — персональні дані (PII) за вимогами GDPR:

- Email, телефон, адреса доставки → AES-256

**Публічні дані** — шифрування недоцільне:

- Назви товарів, ціни, зображення, статуси замовлень → зберігаються відкрито
